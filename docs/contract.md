# Контракт нотаток (заміна Agentation)

Єдине джерело істини для трьох виконавців: сервера, MCP-моста й оверлея.
Хто відступає від цього файлу — ламає двох інших. Зміни контракту йдуть
через диспетчера, не правкою в одному з трьох.

Ролі:
- `comments-harness/server/notes-server.mjs` — HTTP-сервер на :4747, власник даних, арбітр контракту.
- `comments-harness/mcp/notes-mcp.mjs` — MCP stdio-міст, читає й пише через HTTP, свого стану не має.
- `comments-harness/overlay/annotator.tsx` — оверлей у дев-збірці, пише ноти й показує тред.

## Нота

```jsonc
{
  "id": "n-<base36 час><4 випадкові символи>",  // сервер НЕ генерує; шле оверлей
  "createdAt": "2026-08-14T15:57:00.000Z",      // ISO, UTC
  "updatedAt": "2026-08-14T16:10:00.000Z",      // рухає reply, зміна статусу і завантаження кадру
  "status": "pending",                          // "pending" | "working" | "resolved" — інших немає
  "note": "стрілка не має переноситись",        // текст користувача, ≤ 4000 символів

  "url": "http://192.168.1.42:5273/app/client/rewards?as=admin",  // ПОВНИЙ, із query
  "viewport": { "w": 1440, "h": 900 },

  "selector": ".rw-card__title",       // стабільний, унікальний на момент кліку; null якщо не вийшов
  "fullPath": "body > div:nth-child(2) > main > section:nth-of-type(3) > h2",  // завжди є
  "tagName": "h2",
  "classes": "rw-card__title is-active",
  "text": "Your rewards",              // textContent елемента, ≤ 300 символів
  "outerHTML": "<h2 class=…>…</h2>",   // ≤ 2048 символів, довше — обрізати і додати "…"
  "rect": { "x": 120, "y": 340, "w": 280, "h": 32 },   // getBoundingClientRect, округлені

  "components": ["RewardsClient", "Card", "SectionHead"],  // ланцюг знизу вгору, ≤ 8

  "thread": [
    { "role": "agent", "content": "Прибрати всю плитку чи лише підпис?", "at": "2026-08-14T16:05:00.000Z" },
    { "role": "human", "content": "лише підпис", "at": "2026-08-14T16:10:00.000Z" }
  ]
}
```

Правила:
- Полів, яких тут немає, не вигадувати. Мертве з Agentation (`intent`, `severity`,
  `computedStyles`, `placement`, `rearrange`, `nearbyElements`, `accessibility`,
  `sessionId`) не тягнути.
- `thread` порожній масив, а не `undefined`, коли розмови ще не було.
- `selector` може бути `null`; `fullPath` — ніколи. Агент, у якого `selector` не
  матчиться, падає на `fullPath`.
- Статусів рівно три: `pending` (нова, ніхто не взяв), `working` (агент узяв,
  правка в роботі), `resolved` (правку зроблено). Стан «зроблено, чекає на
  перевірку» не існує: результат користувач бачить на екрані, а не в таблиці,
  тож `resolved` живе рівно до того, як сторож складе теку правки
  `data/fixes/<id>/` і перезбере з тек індекс `data/fixlog.md`.
  `working` ставить **агент на старті** — першим ділом, щойно взяв ноту, ще до
  читання коду; `resolved` — після правки.
- `working` — це **видимість, а не блокування**. Гонок за ноту немає (один агент
  на ноту), тож переходи нічим не обмежені: назад у `pending` можна й треба, коли
  агент упав і ноту треба віддати. Сторінка рев'ю (`review/fixlog.html`; у
  `public/` проєкту-господаря лежить лише симлінк на неї) малює такий рядок як
  `.is-wip` — інакше нота стрибає з «нове» одразу в «зникло».
- Закриття ноти — це `DELETE`, а не четвертий статус, і робить його **сторож
  автоматично**, а не людина після перевірки: `watchdog/dispatcher.mjs` пише
  теку `data/fixes/<id>/`, перезбирає з тек індекс `data/fixlog.md` і одразу
  видаляє ноту. `dismissed` = той самий `DELETE`.

## HTTP API (:4747, бінд 0.0.0.0)

| Метод | Шлях | Тіло | Відповідь |
|---|---|---|---|
| `GET` | `/health` | — | `200 {"status":"ok","notes":<число>,"waiting":<число watch-очікувачів>}` |
| `GET` | `/notes` | — | `200 [<нота>, …]`, новіші перші |
| `GET` | `/notes?status=pending\|working\|resolved` | — | `200 [<нота>, …]` відфільтровано; інший статус → `400` |
| `GET` | `/notes/watch?since=<ISO\|мс>&timeout=<с>` | — | `200 [<нота>, …]` коли зʼявилось нове; `200 []` після таймауту; `400` на кривих параметрах |
| `POST` | `/notes` | нота без `updatedAt`/`thread`/`status` | `201 <нота>` \| `400 {"error":…}` |
| `PATCH` | `/notes/:id` | `{"status":"pending"\|"working"\|"resolved"}` або `{"reply":{"role":"agent"\|"human","content":"…"}}` | `200 <нота>` \| `404` \| `400` |
| `DELETE` | `/notes/:id` | — | `204` \| `404` |
| `OPTIONS` | будь-що | — | `204` з CORS-заголовками |

- CORS дозвільний і **обовʼязково** з `Access-Control-Allow-Methods: GET, POST, PATCH, DELETE, OPTIONS`
  та `Access-Control-Allow-Headers: Content-Type`. Сторінка відкривається з іншої
  машини по LAN, тіло JSON → preflight на кожен PATCH/DELETE.
- `PATCH` з `reply` дописує в кінець `thread` і рухає `updatedAt`. Тред ніколи
  не перезаписується і не скорочується.
- `PATCH` зі `status` теж рухає `updatedAt`. Машини станів немає: сервер перевіряє
  лише, що статус із трьох, будь-який перехід дозволений (це дев-інструмент, і
  агент, що впав, мусить уміти перепоставити `pending`).
- Помилка — завжди JSON `{"error":"<текст>"}`, ніколи HTML.

### `/notes/watch` — довге опитування

Єдиний ендпоінт, що не відповідає миттєво: тримає запит відкритим, доки не
станеться подія, новіша за `since`. Подій рівно дві:

1. створено ноту, яка досі `pending` (`createdAt > since`) — нова робота;
2. у тред дописано повідомлення з `role:"human"` (`at > since`) — користувач
   відповів на питання агента.

Реплай самого агента й зміна статусу подіями **не є**: їх робить агент, і
прокидатись від власного запису означало б крутити watch сам на себе. Це
стосується й `working`: узяття ноти watch не будить (правило 1 вимагає
`status === "pending"`, тож узята нота одразу перестає бути новою роботою).

- `since` — ISO або epoch-мілісекунди. Немає → «від цієї миті», тобто беклог
  не віддається (для беклогу є `GET /notes?status=pending`).
- `timeout` — секунди, 1…600, дефолт 60. Вийшов — `200 []`, клієнт просто
  перепитує; не `408`, бо дія клієнта та сама, а помилка в транскрипті агента
  виглядала б поломкою.
- Обірваний клієнт знімається по `req.on('close')` — таймер гаситься,
  очікувач видаляється. Контроль — поле `waiting` в `/health`.
- `GET /notes` лишається синхронним і миттєвим, скільки б хто не висів на watch.

## Ліміти на вхід

`MAX_BODY` 128 КБ; `note` ≤ 4000; `content` реплаї ≤ 4000; `outerHTML` ≤ 2048;
`text` ≤ 300; `components` ≤ 8; `id` ≤ 64 символів і лише `[A-Za-z0-9._-]`.
Усе, що не влізло — обрізає **оверлей**, сервер відхиляє з `400`.

## Зберігання

`comments-harness/data/fixlog-notes.json` — плоский масив нот. Свідомо НЕ в `public/`
проєкту-господаря: усе звідти копіюється в `dist/` і їде на прод, тобто відкриті
ноти — внутрішні зауваження про недороблені екрани — публікувались би публічно.
Шлях сервер рахує від `import.meta.dirname`, не від cwd. У памʼяті read-path, диск —
довговічна копія. Запис у temp + `renameSync` (атомарно). Модель дослівно
скопійована з `comments-harness/server/fixlog-server.mjs` — зазирни туди, там усе вже вирішено.
Файл у `.git/info/exclude`, у git не їде.

## MCP-тули (`notes-mcp.mjs`)

| Тул | Аргументи | Що робить |
|---|---|---|
| `notes_pending` | — | `GET /notes`, лишає відкриті (`pending` + `working`), віддає компактний текст на кожну ноту; статус видно в рядку («new» / «IN PROGRESS»), щоб було ясно, які вже взяті |
| `notes_watch` | `timeout_seconds` (опц., дефолт 60, стеля 600, більше — обрізається) | `GET /notes/watch`, блокується до нової ноти або відповіді користувача; формат виводу як у `notes_pending`, інакше «нічого нового за N с» |
| `notes_get` | `id` | одна нота цілком, включно з тредом |
| `notes_start` | `id` | `PATCH` `{"status":"working"}` — агент викликає **першим**, щойно взяв ноту, ще до читання коду |
| `notes_reply` | `id`, `content` | `PATCH` з `reply` `role:"agent"` — агент перепитує користувача |
| `notes_resolve` | `id` | `PATCH` `{"status":"resolved"}` — після зробленої правки |
| `notes_delete` | `id` | `DELETE` — закриття ноти. У штатному конвеєрі його робить сторож сам, одразу після запису теки правки; тул лишається для ручних випадків (диспетчер у живій сесії, прибирання сміття) |

Реєстрація: `claude mcp add comments-harness -- node <абсолютний шлях до проєкту>/comments-harness/mcp/notes-mcp.mjs`
(шлях мусить бути абсолютний — Claude запускає міст із власного cwd, не з кореня проєкту).
Базовий URL мосту — `http://127.0.0.1:4747` (міст завжди на тій самій машині, що й сервер).

## Знімок анотованого блока (`shot`)

Нота може нести кадр того, що користувач бачив у мить кліку. Це найдешевший
спосіб передати виконавцю **співвідношення** — відступ, збиту кромку, перенос,
іконку, що сидить не на тій лінії. Із `outerHTML` цього не видно взагалі, і
саме через це «виправ вирівнювання» коштувало двох діб очікування відповіді.

Кадр — **довідка, а не критерій приймання**. Виконавець дивиться на нього, щоб
зрозуміти зауваження, і не робить по ньому другий підхід «щоб стало красиво»:
візуальний результат перевіряє людина.

### Де він живе

**Не в JSON.** Кадр блока — це сотні кілобайтів, а `MAX_BODY` стору 128 КБ, і
роздувати плоский файл нот бінарними хвостами не можна: він читається цілком на
кожен запит.

- файл: `comments-harness/data/shots/<id>.png`
- у ноті: `"shot": "shots/n-abc123.png"` — шлях відносно `data/`, або `null`
- у бриф виконавцю йде **абсолютний шлях**, і той читає його як зображення

### API

| Метод | Шлях | Тіло | Відповідь |
|---|---|---|---|
| `POST` | `/notes/:id/shot` | `image/png`, сире тіло | `200 {"shot":"shots/<id>.png"}` \| `404` \| `413` |
| `GET` | `/shots/:file` | — | `200 image/png` \| `404` |

- Окремий запит **після** `POST /notes`: нота існує і без кадру. Знімок не
  вдався — нота все одно доїжджає, з `shot: null`. Кадр ніколи не блокує ноту.
- Ліміт тіла тут свій — `MAX_SHOT` 4 МБ, а не спільний `MAX_BODY`.
- Успішний `POST` кадру **рухає `updatedAt`** ноти, як reply чи зміна статусу.
  Це не дрібниця: рев'ю-сторінка бере `updatedAt` за **наближення** моменту
  «взято в роботу» (власного поля з часом переходу в контракті немає), тож
  список подій, що рухають це поле, треба тримати повним — інакше читач
  вважатиме годинник точнішим, ніж він є.
- `DELETE /notes/:id` прибирає і файл кадру. Інакше `data/shots/` росте вічно.

### Що саме знімається

Не голий елемент. Дефект майже завжди живе **між** елементом і сусідами, тож
кадр береться з полем навколо: елемент плюс ~24 px, а якщо він вужчий за
третину в'юпорта — його батьківський блок. Оверлей на час знімка ховається.

Обмеження: ширина кадру ≤ 1400 px (більше не додає інформації, лише вагу),
масштаб з урахуванням `devicePixelRatio`, але не більше 2×.

# Контракт вердиктів і доробок (:4748)

Другий сервер того самого інструмента — `comments-harness/server/fixlog-server.mjs`.
Він не має нічого спільного зі схемою ноти вище й не читає її: ноти — це
**відкрита робота**, а тут лежать **вердикти по вже закритій** і історія
доробок. Розділ описує його рівно так само, як розділи вище описують :4747,
бо на цей файл посилаються всі, хто пише код тулзи, і дірка в ньому означає,
що правду доводиться вичитувати з трьох реалізацій одразу.

Ролі:
- `comments-harness/server/fixlog-server.mjs` — HTTP-сервер на :4748, власник
  файлу `data/fixlog-ratings.json`, арбітр цього розділу.
- `comments-harness/review/fixlog.html` — рев'ю-сторінка. **Створює** ітерацію
  доробки (кнопка Send back → `POST /rework`) і раз на цикл тягне весь стор
  (`GET /ratings`), щоб намалювати рядки.
- `comments-harness/watchdog/dispatcher.mjs` — сторож. **Закриває** ітерацію:
  опитує `GET /rework`, будує бриф, запускає виконавця й на успіх шле
  `POST /rework-done`.

Більше на цей порт не ходить ніхто — ні оверлей, ні MCP-міст. Розподіл ролей
асиметричний навмисно: людина відкриває ітерацію, машина її закриває. Клієнта,
який робив би обидві дії, немає, і додавати його не треба — саме ця асиметрія
робить «відкрита ітерація» однозначним сигналом «є що доробити».

## Чому це окремий процес і окремий файл

Три сховища тулзи не перетинаються за власником:

- :4747 (`data/fixlog-notes.json`) — робота, яку ще не зроблено;
- `data/fixes/<id>/` — робота, яку зроблено, по теці на правку;
- `data/fixlog.md` — **похідний** індекс, який `server/build-index.mjs`
  перезбирає з тек.

Вердикт не міг лягти в жодне з них. У ноті його нема куди класти — ноти на цей
момент уже не існує (сторож видалив її, щойно склав теку). В індекс — тим
паче: він регенерований, і вердикт, вписаний туди рукою, зникає на першій же
перезбірці. Лишалося або дописувати теки правок, або завести четверте сховище
з власним писарем. Обрано друге, і причина не «мікросервіси», а гонка за файл:
рецензент клацає Send back саме тоді, коли конвеєр пише теки й перезбирає
індекс. Два процеси, що пишуть один файл, рано чи пізно дають або втрачений
вердикт, або половину JSON. Окремий файл + окремий процес знімають питання
цілком, а ціна — один зайвий `node …/fixlog-server.mjs &`.

Побічний наслідок, який теж треба знати: **недоступний :4748 не зупиняє роботу
з нотами**. Сторож ходить на два сервери незалежно, і мовчання вердиктів
означає рівно «доробок сьогодні не візьмемо», а не «конвеєр став».

## Ключ — це `id` теки правки

Запис ключується **іменем теки** `data/fixes/<id>/`: `n-msu1hdbtclmq` для
правки, що прийшла з ноти оверлея, `f-2026-08-10-07` для мігрованих із
рукописного лога. Цей id вічний, тож вердикт лишається пришпиленим до правки
назавжди.

Валідація на сервері: `id` непорожній, ≤ 64 символи, `^[A-Za-z0-9][A-Za-z0-9._-]*$`.
Стеля саме 64 і саме така сама, як у :4747, — ключ походить від id ноти, і
ширша стеля тут дозволяла б завести вердикт під ключем, якого не може мати
жодна правка.

Раніше ключем була пара **«час|роут»**, зіскребена з рядка markdown-таблиці, з
суфіксами `#2`, `#3`, коли дві правки ділили пару. Це був другий носій істини:
рядок індексу перезбирався, час або роут у ньому змінювався — і вердикт
осиротів, а сусідній під тим самим ключем діставав чужу оцінку. Звідси й
відомий симптом «оцінка приїхала не до того рядка».

Старий ключ тепер **відхиляється** з `400` і текстом пояснення, а не тихо
приймається. Це принципово: прийнятий легасі-ключ створив би запис, якого не
покаже жодний рядок рев'ю-сторінки, і помітили б це аж на підрахунку. Гучна
помилка краща за тихий запис у нікуди.

## Запис

```jsonc
{
  "id": "f-2026-08-10-48",          // = ключ у мапі; ім'я теки data/fixes/<id>/
  "updatedAt": "2026-08-10T12:57:32.893Z",  // ISO, рухає будь-який запис у запис

  // Вердикт. Легасі: UI його більше не шле — див. розділ про legacy нижче.
  "stars": 1,                       // ціле 1..5 на вході; у файлі трапляється й 0
  "note": "",                       // текст вердикту, ≤ 4000; '' коли не писали

  // Історія доробок — джерело істини. Масив, а не поле.
  "reworks": [
    {
      "note": "нічого не помінялося. треба виправити",  // ЧОМУ не влаштувало
      "at": "2026-08-10T12:50:40.029Z",                 // коли надіслали (або переписали)
      "done": true,                                     // закрита ітерація?
      "doneAt": "2026-08-10T12:57:32.893Z",             // є лише в закритої
      "result": "прибрав бордер у .bk-row"              // ЩО переробили; опційне
    }
  ],

  // Дзеркало ОСТАННЬОЇ ітерації. Не окрема сутність — копія reworks.at(-1),
  // яку сервер оновлює на кожен запис заради сумісності зі сторожем.
  "rework": { "note": "…", "at": "…", "done": true, "doneAt": "…" }
}
```

Стор загалом — **обʼєкт-мапа** `{ "<id>": <запис>, … }`, не масив. Корінь, який
не є обʼєктом (масив, `null`), сервер вважає зіпсованим стором і **відмовляється
стартувати**, а не починає з порожнього: почати з порожнього означає затерти
єдину копію всіх вердиктів, що коли-небудь ставили.

## `reworks[]` — дерево, а не поле

Кожен Send back — це **одна ітерація**: правку зробили не так, ось слова
рецензента. Правка може піти на коло кілька разів, і кожне коло лишається у
файлі, бо цей файл — **навчальний корпус**: запит → що зробив агент → чому це
відхилили (`note`) → що виправила доробка (`result`). Один слот замість масиву
робив би корпус із рівно одного останнього кола, тобто вирізав би саме те, чим
історія цінна.

Правила:

- Відкритою може бути лише **остання** ітерація. Сервер не дозволяє двом
  ітераціям бути відкритими водночас — черга по правці рівно одна.
- Закриті записи **ніколи не переписуються заднім числом**. `POST /rework-done`
  чіпає тільки останню відкриту; нова ітерація завжди дописується в кінець.
- У ітерації **немає статусу** й не буде. :4748 знає два стани, «відкрита» і
  «закрита», і «взяту в роботу» ітерацію від «нової» не відрізняє. Знання
  «скільки разів я вже це пробував» тримає сторож у себе (`watchdog/state.json`,
  ключ — id правки, значення привʼязане до `at` ітерації). Це свідомо: міняти
  контракт :4748 заради лічильника спроб сторожа не можна, бо лічильник — його
  внутрішня справа, а не факт про правку.

### Відома вада: повторний Send back по відкритій ітерації затирає текст

Якщо ітерація ще **відкрита**, повторний `POST /rework` з тим самим `id` не
дописує другу, а **замінює** `note` і `at` у наявній. Задум був «рецензент
уточнює прохання, а не просить двічі», і для сторожа це працює правильно:
змінений `at` він читає як нове завдання й обнуляє лічильник спроб.

Але попередній текст при цьому **зникає назавжди** — у файлі, який існує саме
заради історії. Це втрата даних, а не фіча: рецензент, що двічі натиснув Send
back, залишає корпусу одну репліку замість двох, і зрозуміти з файлу, що
формулювання змінювалося, неможливо. Описано тут як є; лагодиться це в коді
(наприклад, версіями всередині ітерації), а не редагуванням цього абзацу.

## Легасі-форми, які код і далі читає

Дані старші за поточну схему, і обидва клієнти та сервер читають старі форми
прозоро — **міграційного проходу немає**. Легасі-запис підтягується до нової
форми в момент першого запису в нього, не раніше.

**1. Одиничний слот `rework` замість масиву.** Записи, зроблені до появи
історії, несуть `rework: {…}` і не мають `reworks`. У реальному
`data/fixlog-ratings.json` таких **пʼять** із 38 (`f-2026-08-10-38`, `-48`,
`-56`, `-64`, `-68`), усі закриті. Читання скрізь однакове й повторене втричі
(сервер, сторінка, сторож):

```js
Array.isArray(rec.reworks) ? rec.reworks : rec.rework ? [rec.rework] : []
```

`GET /rework` синтезує плоске дзеркало `rework` і для таких записів, тож
сторож про різницю форм не знає взагалі.

**2. `stars`.** Поле є в **усіх 38** записах файлу, але сторінка його вже не
шле й не показує: у `review/fixlog.html` немає жодного звернення до `/rate` —
тільки `POST /rework` і `GET /ratings`. Тобто **`POST /rate` з боку UI мертвий**.
Ендпоінт лишається живим на сервері (щоб старий клієнт чи `curl` не діставали
404 і щоб запис вердикту не втратив історію доробок — upsert розгортає
попередній запис усередину нового), але штатного клієнта в нього немає.

Розбіжність між кодом і даними, про яку треба знати: сервер приймає `stars`
лише як ціле **1..5**, а у файлі чотири записи мають `stars: 0` — спадок
попереднього сервера, який нуль дозволяв. Поточний `POST /rate` такий запис
створити вже не може, але прочитати його — читає, і нічого з ним не робить.

## HTTP API (:4748, бінд 0.0.0.0)

| Метод | Шлях | Тіло | Відповідь |
|---|---|---|---|
| `GET` | `/health` | — | `200 {"ok":true}` |
| `GET` | `/ratings` | — | `200 {"<id>":<запис>, …}` — весь стор, мапою, без обгортки |
| `POST` | `/rate` | `{"id":"<fix id>","stars":1..5,"note":"…"}` | `200 {"ok":true,"rating":<запис>}` \| `400` \| `500` |
| `POST` | `/rework` | `{"id":"<fix id>","note":"…"}` | `200 {"ok":true,"rating":<запис>}` \| `400` \| `500` |
| `GET` | `/rework` | — | `200 {"count":<число>,"items":[<запис із дзеркалом `rework`>, …]}` |
| `POST` | `/rework-done` | `{"id":"<fix id>","result":"…"}` (`result` опційний) | `200 {"ok":true,"rating":<запис>}` \| `400` \| `404` \| `500` |
| `OPTIONS` | будь-що | — | `204` з CORS-заголовками |
| будь-що інше | — | — | `404 {"ok":false,"error":"no route for <METHOD> <path>"}` |

Деталі, які не влазять у таблицю:

- Помилка — **завжди** JSON `{"ok":false,"error":"<текст>"}`, ніколи HTML.
  Форма `/health` тут своя (`{"ok":true}`) і навмисно не збігається з :4747 —
  сервери різні, спільної схеми здоровʼя між ними немає.
- `POST /rework` без `note` (або з порожнім після `trim`) → `400`: нота **і є**
  інструкція, порожня інструкція безглузда.
- `POST /rework-done` на id, у якого взагалі немає ітерацій → `404`. На id, у
  якого остання ітерація вже закрита, → `200` з наявним записом, **не** помилка:
  повторний POST після обірваної відповіді мусить бути ідемпотентним, інакше
  сторож бачив би 404 там, де робота насправді зарахована.
- `result` в `/rework-done` опційний і додається до ітерації, лише якщо
  непорожній. Це відповідь корпусу на «що виправила доробка».
- `updatedAt` рухає будь-який успішний запис — і `/rate`, і `/rework`, і
  `/rework-done`.
- Кожна відповідь іде з `Cache-Control: no-store`: сторінка перечитує стор на
  кожному циклі й не має права дістати 304-кешований знімок чужої сесії.
- Довгого очікування (аналога `/notes/watch`) тут **немає** і не планується.
  Сторож тому опитує `GET /rework` таймером (дефолт 60 с, `WATCHDOG_REWORK_POLL_S`).
  Черга гарячою не буває: між «людина подивилась правку» і «натиснула Send back»
  минають хвилини.
- Базовий URL сторожа — `RATINGS_URL`, дефолт `http://127.0.0.1:4748`.
  Сторінка адресу не конфігурує взагалі: `http://${location.hostname}:4748`
  зашито в `review/fixlog.html`, а порт — константа в сервері. Міняти обидва
  місця треба разом; значення, яке читає лише одна сторона, — це тиха розбіжність.

## Ліміти на вхід і CORS

`MAX_BODY` **64 КБ** (вдвічі менше, ніж у :4747: тут немає ні `outerHTML`, ні
кадрів, один вердикт важить ~200 байтів, решта — шум); `id` ≤ **64** символи й
лише `[A-Za-z0-9._-]` з літери/цифри на початку; `note` ≤ **4000**; `result`
≤ **4000**.

Довгий текст **відхиляється з `400`, а не обрізається**. Обрізати — це
відповісти `ok: true` рецензентові, у якого щойно викинули останній абзац, і
ніде про це не сказати; а для `/rework` обрізана інструкція — це ще й доробка,
зроблена не за тим завданням.

Тіло, більше за `MAX_BODY`, зупиняє читання, але **не рве сокет**: інакше `400`
з поясненням пішов би в мертве зʼєднання й клієнт побачив би обрив замість
єдиної обіцянки цього сервера — «помилка завжди JSON».

CORS дозвільний і обовʼязково з `Access-Control-Allow-Methods: GET, POST, OPTIONS`
та `Access-Control-Allow-Headers: Content-Type`, `OPTIONS` → `204`. Причина та
сама, що й на :4747: сторінку відкривають з іншої машини по LAN (dev-сервер
слухає 0.0.0.0), тож для браузера `http://192.168.1.42:5273` → `:4748` це
крос-орігін, і preflight летить на кожен POST із JSON-тілом. Без цього кожен
POST падає непрозорим «Failed to fetch». Порт 4748 відкритий у ufw **лише** для
192.168.1.0/24.

## Зберігання

`comments-harness/data/fixlog-ratings.json` — мапа, ключ = id правки. Шлях
рахується від `import.meta.dirname`, не від cwd. Читання — з памʼяті (`GET`
диска не торкається), диск — довговічна копія; файл вантажиться **раз на
старті**, тож зіпсований стор помітно одразу при запуску, а не на першому
запиті через годину. Запис — у temp-файл **у тій самій теці** плюс
`renameSync`: rename атомарний у межах однієї ФС, тож читач бачить або старий
файл, або новий, і ніколи половину. Якщо запис не вдався, памʼять **не**
оновлюється — стор не має права заявляти довговічність, якої не має, і сторінка
показує помилку.

Рев'ю-сторінка читає цей самий файл ще й по HTTP, бо `public/fixlog-ratings.json`
у проєкті-господарі — симлінк на нього. Канонічна копія лишається всередині
`comments-harness/`, щоб інструмент переносився цілим.
