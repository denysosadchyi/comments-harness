# Тека на правку — джерело істини

## Навіщо

До цієї схеми одна правка була розкидана по пʼятьох місцях: нота в
`fixlog-notes.json`, кадр у `data/shots/`, лог прогону у `watchdog/runs/`,
рядок у `fixlog.md`, оцінка в `fixlog-ratings.json`. Три з них губилися, щойно
ноту закрито.

Але головне було не в охайності, а у **відсутності постійного імені**. Після
закриття `id` ноти зникав, і рейтинги ключувалися рядком `час|роут` — через це
в коді жив костур із суфіксами `#2`, `#3` на випадок збігу пари. Тека, названа
`id`, дала правці вічне імʼя, і цей клас помилок («оцінка приїхала не до того
рядка») зник разом із костуром: :4748 тепер приймає лише імʼя теки, а старий
ключ відхиляє з `400`.

## Що чим стає

- **Тека правки — джерело істини.** Усе про одну правку лежить в одному місці.
- **`fixlog.md` — похідний індекс**, який генерується з тек. Він лишається, бо
  один файл, який людина гортає й грепає, — це справжня цінність, і втрачати її
  не можна. Але руками його більше ніхто не редагує.
- **Черга (`fixlog-notes.json`) лишається плоским JSON.** Вона маленька,
  самоочисна й читається цілком на кожен запит; тека там нічого не додає.

Тобто тека зʼявляється **в момент закриття** ноти, а не створення.

## Розкладка

```
data/fixes/<id>/
  fix.json      метадані (нижче)          — є в кожній теці
  note.md       запит користувача + тред  — є в кожній теці
  run.log       вивід виконавця           — лише якщо правку робив сторож
  shot.png      кадр анотованого блока    — лише якщо кадр був
```

Це весь склад теки **на сьогодні**. Вердикти й доробки в теку ще не переїхали:
вони й далі живуть у `data/fixlog-ratings.json`, який пише :4748 (див.
`review-page.md`). Задум віддати теці й це — `rework/` із файлами ітерацій
(`01.md`, `02.md`…) і `rating.json` з оцінкою — лишається в силі, але **жодної
такої теки зараз не існує**, і код їх не пише й не читає. Мігровані з
`fixlog.md` рядки складаються з двох файлів: `fix.json` і `note.md`.

## Тека не знає про доробки — визнаний розрив

Це найважливіша неправда, яку тека може сказати читачеві, тож вона названа тут
прямо.

Правку можуть **переробити**: користувач тисне Send back, сторож бере ітерацію
з другої черги й запускає виконавця, той міняє файли (див. `watchdog.md`). Але
теку правки цей шлях **не чіпає взагалі** — ні успішна гілка, ні провальна.
Тобто:

- `did` і `files` у `fix.json` описують **перший** підхід і після доробки
  стають застарілими: у файлах уже інше, а тека про це не знає;
- `note.md` тримає початковий запит і тред ноти — претензії «не влаштувало»
  там немає й не буде, ноти на той момент уже не існує;
- `run.log` у теці — лог **того** прогону, що складав теку. Логи доробок
  лишаються в `watchdog/runs/<id>-rework-<час>.log` і нікуди не переїжджають.

Уся історія другого й наступних підходів живе **тільки** в
`data/fixlog-ratings.json`, у масиві `reworks[]`: пари «чому не влаштувало
(`note`) → що переробили (`result`)». Звʼязок односторонній — від запису
вердиктів до теки через спільний `id`; від теки до доробок звʼязку немає
жодного.

Наслідок практичний: **тека самодостатня тільки до першого Send back**. Хто
читає теку, щоб зрозуміти правку, мусить знати про існування другого файлу,
інакше прочитає першу спробу як остаточну.

Пропозиція закрити розрив є — лишати слід у самій теці, наприклад `reworks.log`
поруч із `fix.json`, дописуваний на кожну закриту ітерацію, — але вона
**не реалізована**: такого файлу немає в жодній теці, і код його не пише.
Розділ описує стан як є, а не як задумано.

`<id>` — це `id` ноти (`n-msu1hdbtclmq`), він уже унікальний і вже стоїть у
рядках лога. Для мігрованих рядків, у яких id ніколи не було, — `f-<дата>-<NN>`
за порядком появи в `fixlog.md`.

## `fix.json`

```jsonc
{
  "id": "n-msu2ap8uz2sj",
  "createdAt": "2026-08-15T07:35:59.000Z",   // коли користувач поставив ноту
  "closedAt":  "2026-08-15T07:42:11.000Z",   // коли сторож закрив
  "durationMs": 372000,                       // прогін виконавця, не час лежання; null, якщо тривалості немає (мігровані рядки, ручні правки)

  "note": "прибери лінію",
  "url": "http://localhost:5173/app/client/my-packages",
  "route": "/app/client/my-packages",         // похідне від url, для індексу
  "selector": "hr.sm-antform__divider:nth-of-type(3)",
  "fullPath": "body > … > hr:nth-of-type(3)",
  "tagName": "hr", "classes": "sm-antform__divider",
  "components": ["MyCredits", "App"],
  "rect": { "x": 0, "y": 0, "w": 0, "h": 0 },
  "viewport": { "w": 1421, "h": 1224 },

  "lane": "claude",                           // хто робив: claude | opencode | self
  "agent": "Opus 5",                          // точна назва, для title
  "did": "Прибрано третій <hr> між фільтром і списком…",
  "files": ["src/app/client/MyCredits.tsx"],  // чого торкнувся виконавець
  "shot": "shot.png",                          // або null
  "outcome": "done",                           // done | dismissed

  /* Слід міграції з `fixlog.md`: як рядок виглядав у markdown до розбору.
     Є майже в кожній теці (усі мігровані рядки), немає у свіжих теках, які
     сторож пише з живої ноти. На нього спирається генератор індексу
     (`server/build-index.mjs`): рукописні комірки — час, тривалість прозою,
     роут, підпис агента — віддаються з `source` дослівно, а не
     переформатовуються, інакше перезбір індексу переписав би текст, який
     колись друкувала людина. Порядок рядків у розділі теж звідси
     (`source.line`), тож теки без `source` йдуть після мігрованих того ж дня. */
  "source": {
    "file": "fixlog.md", "line": 21, "date": "2026-08-10",
    "section": "До запуску автомата — робив я вручну",
    "timeRaw": "09:37", "durationRaw": null,
    "routeCell": "`/auth/sign-in`", "noteIdSuffix": null, "agentRaw": "agent"
  }
}
```

Полів, яких тут немає, не вигадувати — те саме правило, що й для ноти. Але
`source` саме є, і викидати його не можна: без нього індекс перезбереться
іншим текстом і іншим порядком.

## Правила

- Тека **незмінна після створення**: правка вже сталася, переписувати її заднім
  числом нема чого. Виняток передбачено на майбутнє — те, що додається **після**
  правки (доробки й оцінка); поки що вони лежать не тут, а у
  `data/fixlog-ratings.json`.
- `fixlog.md` **перегенеровується** з тек, а не дописується. Рядок індексу несе
  `id`, тож від рядка завжди можна дійти до теки.
- Видалення теки = видалення правки з історії. Цього не робить ніхто
  автоматично — і генератор індексу цьому свідомо заважає. `buildIndex()`
  перезаписує `fixlog.md` **цілком**, тож нечитабельний `fix.json` тихо викинув
  би правку з єдиного файлу, який людина грепає, і виклик відрапортував би
  успіх. Тому запобіжник: **зібрано менше тек, ніж уже є рядків в індексі —
  це аварія**, `buildIndex()` кидає, старий індекс лишається недоторканим.
  Виняток один і навмисний: `buildIndex({ allowShrink: true })` — коли теку
  видалили **свідомо** (тестовий запис, дубль) і хочуть, щоб індекс це
  відобразив. Без цього прапорця запобіжник ставав би глухим кутом: після
  ручного видалення індекс не перезбирався б ніколи, кожен наступний виклик
  падав би. За замовчуванням він вимкнений, тож автоматичний шлях (сторож)
  захищений.
- Тека самодостатня: її можна переслати, показати, видалити, і вона не тягне за
  собою решту сховища. З однією поправкою — див. розділ про доробки вище:
  після Send back частина правди про правку лежить уже не в теці.
