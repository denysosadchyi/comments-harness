# Архітектура

Пʼять частин, одна з них — власник даних, решта до неї ходять по HTTP.
Це не результат розростання: кожна межа тут проведена свідомо, і нижче сказано,
чого коштувало б її стерти.

```
        ┌───────────────────────┐
        │  Оверлей (дев-збірка) │  overlay/annotator.tsx
        │  приціл · поповер ·   │
        │  маркери · тред       │
        └───────┬───────────────┘
                │ POST /notes · PATCH /notes/:id (reply role:"human")
                │ GET /notes  (свій опитувальник, 8 с)
                ▼
        ┌───────────────────────┐         ┌──────────────────────────┐
        │  Сервер нот  :4747    │◄────────┤  MCP-міст (stdio)        │
        │  server/notes-server  │  HTTP   │  mcp/notes-mcp.mjs       │
        │  ВЛАСНИК ДАНИХ        ├────────►│  7 тулів, нуль стану     │
        └──┬────────────────┬───┘         └──────────┬───────────────┘
           │                │                        │ stdio JSON-RPC
           │ GET /notes     │ GET /notes/watch        ▼
           │                │ (довгий полінг)  ┌──────────────┐
           │                │                  │  Агент/Claude│
           │                ▼                  └──────────────┘
           │        ┌───────────────────────┐         ▲
           │        │  Сторож (демон)       │         │ spawn claude -p
           │        │  watchdog/dispatcher  ├─────────┘
           │        └───────────┬───────────┘
           │                    │ тека правки → перезбір індексу → DELETE ноти
           │                    ▼
           │              data/fixes/<id>/
           │                    │ buildIndex()  (server/build-index.mjs)
           │                    ▼
           │              data/fixlog.md
           ▼
        ┌───────────────────────┐  review/fixlog.html
        │  Рев'ю-сторінка       │
        │  таблиця + вердикти   │
        └───┬───────────────┬───┘
            │ fetch         │ вердикти й доробки
            │ /fixlog.md    ▼
            │        ┌──────────────────────────┐
            ▼        │  Сервер рейтингів :4748  │
      data/fixlog.md │  server/fixlog-server    ├──► data/fixlog-ratings.json
                     └──────────────────────────┘        доробки (reworks[])
```

На схемі не намальована ще одна стрілка: сторож ходить і на :4748 —
`GET /rework` (друга черга, доробки) і `POST /rework-done`. Тобто :4748 має
двох клієнтів, а не одну лише рев'ю-сторінку.

## Хто чим володіє

**Сервер нот — єдиний власник даних і єдиний арбітр контракту.** Ні міст, ні
оверлей не тримають свого стану: кожна дія — це один HTTP-запит і назад.
Спокуса кешувати список нот у мості велика (це ж просто масив), і саме тому
вона названа тут окремо: черга рухається у браузері, і закешований міст
упевнено вручив би агентові ноту, яку користувач хвилину тому закрив.

З тієї ж причини валідація живе тільки на сервері й вона строга. Нота, що
пролізла кривою, — це нота, від якої два інші процеси мусять захищатись вічно.
Обрізання довгих полів (`outerHTML`, `text`) — навпаки, робота **оверлея**:
усе, що приїхало понад ліміт, це клієнт, який зігнорував контракт, і йому
віддається `400`, а не тихий трим, що сховав би баг.

**Нота — це відкрита робота.** Закриття — `DELETE`, а не четвертий статус.
Історія зробленого належить **текам правок** (`data/fixes/<id>/`), які складає
сторож на кожен `resolved`; плаский `data/fixlog.md` — не журнал, куди дописують
рядок, а **похідний індекс**, який сторож перезбирає з тек цілком
(`buildIndex()` із `server/build-index.mjs`) щоразу після запису теки. Порядок
жорсткий: тека → індекс → `DELETE` ноти. Змішати історію з чергою означало б
зробити сервер нот ще й архівом — з міграціями, пагінацією й рештою, чого
дев-інструменту не треба.

**Статусів рівно три**, і середній не є замком. `working` існує заради
**видимості**: один агент працює над однією нотою, гонки нема чого стерегти. А
є користувач, який без цього статусу бачить, як його зауваження стрибає з
«нове» одразу в «зникло». Оскільки це не замок, переходи не полісяться взагалі:
агент, що впав посеред правки, мусить мати змогу повернути ноту в `pending`, а
машина станів на сервері зробила б це відновлення ззовні неможливим.

## Потік даних, крок за кроком

1. Користувач тицяє елемент. Оверлей рахує **стабільний селектор**, повний
   `fullPath`, `tagName`, класи, текст, обрізаний `outerHTML`, `rect`, viewport
   і ланцюг React-компонентів знизу вгору. Ці поля — це те, чим агент замінює
   пошук наосліп, тож збираються вони на місці кліку й більше ніде.
2. `POST /notes`. Id генерує **оверлей**, не сервер: нота має ідентичність ще
   до того, як полетить запит, інакше маркер на екрані не має за що зачепитись.
3. Сервер валідує, кладе в памʼять, пише на диск через temp + `rename` (атомарно
   в межах одної ФС) і **будить сторожів** (див. `watchdog.md`).
4. Диспетчер, що висів на `notes_watch`, отримує ноту й віддає її агентові.
5. Агент: `notes_start` → правка → `notes_resolve`. Може перепитати
   (`notes_reply`, `role:"agent"`), і відповідь користувач друкує просто в
   оверлеї (`role:"human"`) — це другий тип події, що будить сторожа.
6. Сторож, побачивши `resolved`, складає теку `data/fixes/<id>/`, перезбирає
   з тек `fixlog.md` і **сам** видаляє ноту — без людини в цьому кроці.
7. Рев'ю-сторінка раз на десять секунд перечитує `GET /notes`, домальовує архів
   із `fixlog.md` і вердикти з :4748. Щосекунди цокають лише живі лічильники
   часу — окремим таймером, бо лічильник, що рухається раз на десять секунд,
   виглядає замерзлим.
8. Користувач дивиться очима на екран застосунку. Не влаштувало — Send back,
   і це вже не повернення ноти (її немає), а нова ітерація доробки на :4748.
9. Сторож опитує другу чергу (`GET :4748/rework`) і на кожну відкриту ітерацію
   запускає виконавця з окремим брифом — контекст для нього береться з теки
   правки, бо ноти вже немає. Переробив — сторож закриває ітерацію
   (`POST /rework-done`); не переробив — вона лишається відкритою.

## Чому нуль залежностей

Обидва сервери й міст — на голому `node:http` / `node:readline`. Це не
аскетизм, це тривкість:

- Тулза дев-часу не має права лежати в `package.json` проєкту-господаря — вона
  не залежність продукту. А те, що ставлять `--no-save`, наступний звичайний
  `npm install` вирізає як extraneous. Тобто маршрут «поставити MCP SDK
  тимчасово» закінчується мостом, який одного дня мовчки перестає стартувати з
  `ERR_MODULE_NOT_FOUND` десь усередині запуску MCP, де ніхто не дивиться.
- Stdio-MCP — це JSON-RPC 2.0 по рядках із чотирма методами, що мають значення
  (`initialize`, `notifications/initialized`, `tools/list`, `tools/call`).
  Це ~80 рядків, які ніколи не змінюються. SDK тут економить менше, ніж коштує.
- Сервери піднімаються руками (`node …&`), переживають будь-яку зміну
  lockfile і не мають чому зламатись від чужого оновлення.

Наслідок для переносу: тека копіюється в інший проєкт **як є**, і єдине, що
треба зробити, — примонтувати оверлей і віддати рев'ю-сторінку по HTTP.

## Чому саме HTTP, а не файл

Спокусливо було б обійтись одним JSON-файлом, який усі троє читають і пишуть.
Не працює з двох причин. По-перше, оверлей живе у браузері — файлової системи
в нього немає взагалі. По-друге, довгий полінг (`/notes/watch`) — це саме те,
заради чого сторож існує, а на файлі він перетворюється на `fs.watch` із
дебаунсом, гонками й окремою поведінкою на кожній ОС.

## Два сервери, а не один

:4747 тримає **відкриту роботу**, :4748 — **вердикти й доробки**. Це різні
життєві цикли: нота живе години й видаляється, вердикт живе вічно й накопичує
історію ітерацій. Злиття дало б один процес, у якому видалення ноти або стирало
б історію її оцінок, або лишало б сироту. Деталі — у `review-page.md`.
